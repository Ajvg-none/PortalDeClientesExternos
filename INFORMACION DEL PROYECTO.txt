STACK TECNOLOGICO

Stack Tecnológico
Frontend: React 18 como librería para construir la interfaz de usuario como una aplicación de una sola página (SPA), junto con Vite como herramienta de build y entorno de desarrollo rápido.
Backend: Node.js en su versión 20 LTS como runtime de JavaScript del lado del servidor, y Express.js como framework para construir la API REST de manera sencilla y flexible.
ORM: Prisma como capa de acceso a la base de datos, facilitando consultas tipadas, migraciones y manejo de modelos.
Base de datos: PostgreSQL en su versión 16, base de datos relacional robusta que almacena usuarios, órdenes y la API Key.
Autenticación: JWT (JSON Web Tokens) para manejar sesiones de usuarios de forma stateless, y bcryptjs para aplicar hash seguro a las contraseñas.
Integración externa: API Key en el header X-API-Key para autenticar las peticiones del middleware externo.
Despliegue: Docker para contenerizar los servicios y Docker Compose para orquestar los contenedores en el entorno de desarrollo y producción.
Control de versiones: Git como sistema de control de versiones del código fuente.
Documentación de API: OpenAPI/Swagger como estándar opcional para documentar los contratos de la API, especialmente los endpoints de integración.
Herramientas de desarrollo y testing: Nodemon para recarga automática del backend durante desarrollo, Jest como framework de pruebas unitarias y de integración, Supertest para probar endpoints HTTP, morgan para registrar las peticiones y express-validator para validar los datos de entrada en las rutas.

REQUISITOS FUNCIONALES DEL PROYECTO

Descripción y Contexto del Software
Portal de Clientes Externos - Sistema de Gestión de Órdenes Ópticas
Contexto
Nuestra empresa es una cadena óptica con presencia a nivel nacional que cuenta con su propio laboratorio de producción. Este laboratorio nos permite ofrecer servicios de fabricación de lentes no solo para nuestras propias tiendas, sino también para otras ópticas independientes que requieren tercerizar su producción.
Actualmente, las tiendas de nuestra cadena operan con un sistema SaaS de facturación y gestión administrativa, el cual se integra con nuestro laboratorio a través de un middleware que extrae las órdenes y genera los tickets de producción y VCA (Vale de Compra Automatizada).
El desafío surge al no contar con un canal formal y digital para que las ópticas externas (nuestros clientes) puedan solicitar trabajos ópticos de manera ordenada y trazable, gestionando las órdenes en un solo lugar y garantizando la integración con nuestro flujo de producción actual.
Solución Desarrollada
Portal de Clientes Externos es una plataforma web diseñada específicamente para gestionar el ciclo de vida de las órdenes ópticas provenientes de clientes externos (ópticas asociadas). Este sistema permite:
•	A las ópticas clientes: Crear y gestionar sus órdenes de trabajo de manera autónoma, ingresando todos los datos ópticos necesarios (fórmula, tratamiento, montura, coloración) desde un panel intuitivo y seguro.
•	Al laboratorio: Visualizar en tiempo real todas las órdenes entrantes de todos los clientes en un único tablero, facilitando la planificación de la producción.
•	A los administradores: Gestionar usuarios (altas, bajas, roles), monitorear el flujo de órdenes y acceder a estadísticas y reportes para la toma de decisiones.
La solución se integra de manera transparente con la infraestructura tecnológica existente: el middleware actual (desarrollado previamente) se ha extendido para consumir órdenes desde este nuevo portal, asegurando que las órdenes de clientes externos sigan el mismo flujo de producción que las órdenes de nuestras tiendas internas.
De esta forma, centralizamos la recepción de pedidos de terceros, eliminamos procesos manuales, reducimos errores de captura y mejoramos la experiencia de nuestros clientes externos, todo mientras maximizamos el uso de nuestra capacidad productiva.

Módulo 5: Integración con el Middleware (Modelo PULL)
5.1. Endpoint para que el middleware consulte órdenes
•	RF-35: El portal debe exponer un endpoint REST GET /api/external-orders/pending que el middleware consultará periódicamente para obtener órdenes pendientes de sincronización.
•	RF-36: El endpoint debe devolver solo las órdenes que estén marcadas como "Pendiente de sincronización".
•	RF-37: El endpoint debe soportar paginación para que el middleware pueda consumir las órdenes una por una o en lotes, evitando saltos y desperfectos. Parámetros de paginación:
o	limit (opcional): cantidad de órdenes por página (valor por defecto: 10)
o	offset (opcional): desplazamiento para la paginación
•	RF-38: Cada orden devuelta debe incluir todos los datos del formulario en el formato JSON canónico acordado.
5.2. Autenticación del endpoint
•	RF-39: El endpoint debe estar protegido con API Key.
•	RF-40: La API Key debe ser única y estática, configurada una sola vez en el portal (no generable automáticamente).
•	RF-41: El middleware usará esta API Key en el header X-API-Key para autenticarse.
5.3. Lógica de sincronización
•	RF-42: El middleware es quien consulta al portal. El portal no inicia ninguna comunicación.
•	RF-43: Cuando el middleware consulta el endpoint y obtiene una orden, es responsabilidad del middleware procesarla e inyectarla en su pipeline.
•	RF-44: El portal no sabe si el middleware procesó exitosamente la orden. El portal solo entrega las órdenes pendientes cuando se las solicitan.
•	RF-45: El portal debe tener un mecanismo para que el middleware marque una orden como sincronizada después de procesarla. Esto puede ser:
o	Opción A: El middleware hace un PUT /api/external-orders/:id/sync para marcar la orden como sincronizada.
o	Opción B: El middleware incluye un campo en la consulta para que el portal devuelva las órdenes y automáticamente las marque como "En proceso" o "Sincronizada".
•	RF-46: Se recomienda la Opción A (endpoint separado para marcar sincronización), para que el portal tenga control claro de qué órdenes ya fueron tomadas.
•	RF-47: El administrador debe poder ver en el listado maestro el estado de sincronización de cada orden: "Pendiente" o "Sincronizada".

5.5. Endpoint para marcar sincronización
•	RF-49: El portal debe exponer un endpoint PUT /api/external-orders/:externalId/sync para que el middleware marque una orden como sincronizada después de procesarla.

Módulo 7: Flujo de Trabajo
Flujo completo del sistema:
1.	Cliente → inicia sesión, llena formulario (incluyendo su propio Número de Orden) y envía.
2.	Sistema → valida que el Número de Orden sea único y guarda la orden con estado "Pendiente de sincronización".
3.	Laboratorio → inicia sesión y visualiza todas las órdenes de todos los clientes (solo lectura).
4.	Middleware → consulta periódicamente GET /api/external-orders/pending y obtiene las órdenes pendientes.
5.	Middleware → procesa cada orden (genera VCA, imprime, etc.) y la inyecta en su pipeline.
6.	Middleware → una vez procesada, hace PUT /api/external-orders/:externalId/sync para marcar la orden como "Sincronizada".
7.	Administrador → visualiza todas las órdenes y su estado de sincronización.

2. Decisiones UI/UX: ¿Página o modal?
A continuación se detalla cuándo usar una página independiente y cuándo un modal, justificando cada decisión.
Formulario de nueva orden → Página separada
•	El formulario contiene decenas de campos: datos generales, siete campos para OD, siete para OI, tratamiento (select), montura (tipo, marca, modelo, color), coloración (color, unicolor checkbox, degradado %) y observaciones.
•	Un modal sería demasiado extenso, obligaría a hacer scroll interno y dificultaría la usabilidad.
•	Una página dedicada permite una mejor distribución en varias secciones, validaciones en tiempo real, manejo de errores y navegación fluida.
Resumen de orden previo al envío → Modal
•	Es un paso intermedio de verificación antes de enviar la orden.
•	Un modal superpuesto al formulario permite al usuario revisar los datos sin perder el contexto del formulario.
•	Si algo está mal, puede cerrar el modal y corregir fácilmente.
•	Se muestra un resumen legible con todos los campos ingresados.
Detalle de orden (cualquier rol) → Página separada
•	El detalle contiene mucha información: todos los datos ópticos, tratamiento, montura, coloración y observaciones.
•	Una página permite una visualización clara y estructurada, con posibilidad de incluir secciones o incluso una vista de impresión.
•	Se puede volver al listado con un botón "Atrás" sin perder el estado de los filtros (si se usa navegación con estado).
Formulario de creación/edición de usuario → Página separada
•	Similar al formulario de orden: campos diversos (empresa, email, teléfono, dirección, contraseña temporal).
•	Mejor en página para evitar modales grandes y permitir validaciones completas (por ejemplo, confirmación de contraseña).
Confirmación de eliminación de usuario → Modal (diálogo de confirmación)
•	Es una acción destructiva; el estándar es un modal pequeño con mensaje de advertencia y botones "Cancelar" / "Eliminar".
•	Evita eliminaciones accidentales.
Resetear contraseña → Modal o acción directa
•	Se recomienda un modal de confirmación para evitar acciones accidentales.
•	Puede incluir un campo para ingresar la nueva contraseña o un botón para generarla automáticamente.
Filtros en listados → Controles en la misma página
•	Los filtros (rango de fechas, cliente, estado de sincronización) son parte integral del listado.
•	Se ubican en la parte superior de la tabla, sin necesidad de modales.
•	Se incluyen botones "Aplicar filtros" y "Limpiar".
Gráficos estadísticos → Página dashboard
•	Los gráficos requieren espacio y contexto, por lo que una página dedicada es lo adecuado.
•	Se pueden incluir tarjetas de totales y gráficos interactivos.

ANEXO: ACLARACIONES DE PUNTOS CRITICOS - DECISIONES v1
Reglas base de este anexo:
- Construir la PLATAFORMA primero. No se asume ningun comportamiento interno del middleware (reintentos,
  tiempos de poll, deduplicacion, ni el resultado de su procesamiento).
- Formateo y envio de datos: el unico mecanismo definido es el endpoint GET /api/external-orders/pending
  (RF-35 a RF-38), que entrega el JSON canonico de las ordenes pendientes cuando el middleware lo consulta
  (modelo PULL). El portal nunca inicia comunicacion (RF-42).
- El middleware confirma con PUT /api/external-orders/:externalId/sync (RF-49) cuando corresponde.
- Este anexo NO reemplaza los RF existentes: aclara los puntos criticos y fija las decisiones de v1.

PC-1. Estados de sincronizacion y riesgo de doble entrega (aclara RF-44, RF-45, RF-46 y RF-53)
- Se mantienen SOLO dos estados: 'Pendiente de sincronizacion' y 'Sincronizada' (RF-53). La Opcion B de
  RF-45 queda descartada (no existe estado 'En proceso' en v1). La Opcion A de RF-46 es la unica via de
  sincronizacion: el middleware confirma con PUT /sync.
- El GET /pending NO cambia el estado de las ordenes al entregarlas. Entregar una orden no la saca del
  listado de pendientes: una orden deja de entregarse SOLO cuando el middleware la confirma con PUT /sync.
- Consecuencia aceptada y documentada (entrega tipo 'al menos una vez'): si el middleware recibe una
  orden pero nunca la confirma, esa orden se seguira entregando en los proximos polls. El portal no puede
  distinguir 'el middleware no la proceso' de 'el middleware la proceso pero no confirmo' (RF-44), y no
  asume ninguna de las dos situaciones.
- Medidas que toma el PORTAL (no dependen del middleware):
  a) PUT /sync idempotente: confirmar una orden ya sincronizada responde HTTP 200 sin error ni cambio de
     estado (una confirmacion repetida no rompe nada en el portal).
  b) El portal registra created_at (creacion de la orden) y synced_at (momento de la confirmacion).
  c) El listado maestro del administrador (RF-29/RF-31) muestra ademas la antiguedad 'pendiente desde',
     para detectar ordenes estancadas. Detectar/escalar una orden estancada al equipo del middleware es
     un procedimiento operativo, no una funcion del sistema en v1.
- Fuera de alcance v1: garantizar entrega unica (exactly-once). Si el negocio lo exige mas adelante, se
  evaluara un estado intermedio (tipo 'EN_PROCESO', reclamando la orden al entregarla) junto con
  paginacion por cursor; eso implica acordar un nuevo contrato con el middleware y NO se disena ahora.

PC-2. Paginacion del endpoint de pendientes sin saltos (aclara RF-37)
- El GET /pending ordena SIEMPRE por created_at ASC y id ASC (las ordenes mas antiguas primero, FIFO),
  para que el orden de entrega sea estable entre peticiones.
- El GET es de solo lectura (ver PC-1): no elimina ni marca ordenes al entregarlas. El conjunto de
  'pendientes' solo cambia cuando el middleware confirma syncs (PUT /sync).
- Con paginacion limit/offset, se producen saltos si el conjunto cambia mientras se pagina (cada sync
  quita ordenes y el offset se corre). Para que el contrato sea seguro, el patron de consumo soportado en
  v1 es uno de estos dos:
  1) Un ciclo de sincronizacion = UNA sola peticion (offset=0 y limit = tamano del lote deseado), o
  2) Varias peticiones secuenciales (offset=0, limit, 2*limit, ...) hasta cubrir el 'total' devuelto, y
     recien DESPUES de recorrer todas las paginas se confirman los syncs de ese ciclo.
  Regla: no intercalar GET y PUT /sync dentro del mismo ciclo (cada confirmacion mueve el offset y se
  saltan ordenes o se entregan repetidas).
- Esta regla forma parte del CONTRATO del endpoint (documenta como debe consumirse); no es una suposicion
  sobre la implementacion interna del middleware.
- Indice recomendado para el endpoint de pendientes: indice compuesto (sync_status, created_at, id), que
  evita ordenar toda la tabla en cada consulta.

PC-3. Ordenes que el middleware no puede procesar (aclara RF-44; no hay 'dead letter' en v1)
- El portal no recibe el resultado del procesamiento del middleware (RF-44) y no asume como reacciona el
  middleware ante una orden que no puede procesar. Por eso NO se modela un estado de error/rechazo en v1.
- Comportamiento del portal ante una orden que queda sin confirmar: permanece 'Pendiente de
  sincronizacion' (se seguira entregando, ver PC-1) y queda visible en el listado del administrador con
  su antiguedad ('pendiente desde'). Esa visibilidad es la senal para escalar manualmente al equipo del
  middleware.
- Si al trabajar la integracion surge la necesidad de un estado de error o de retirar una orden del flujo,
  se agregara como nuevo requerimiento; hoy no se disena para no asumir el comportamiento del middleware.

PC-4. Contrato JSON vs. datos que el portal realmente almacena (aclara RF-38 y RF-48)
El portal construye el JSON de respuesta UNICAMENTE con datos que puede llenar con certeza:
- Del formulario / base de datos: number (= Numero de Orden del cliente), date (fecha de creacion de la
  orden), customer {company, patient}, opticalDataOD, opticalDataOI, treatment, mount {type, brand,
  model, color}, coloration y observations.
- Constantes del portal: orderFromSupplier = true y status = 'CONFIRMED'. Son valores fijos para toda
  orden creada en el portal.
- Campos del ejemplo RF-48 que el portal NO puede poblar y que NO se entregan en v1 (su valor solo puede
  originarse en el middleware; se retoman cuando se defina la integracion con su fuente):
  a) warehouse {id, name}: el portal no administra bodegas/sucursales. El mapeo empresa -> bodega lo
     conoce el middleware, o se agrega como modulo de datos maestros en el futuro.
  b) issuedOrderId e issuedInvoiceId: los genera el pipeline del middleware al procesar. Devolverlos al
     portal exigiria que el PUT /sync enviara datos de vuelta (write-back); mejora futura, fuera de v1.
  c) items[]: la descripcion (ej. 'Lente Progresivo') proviene del catalogo de productos del middleware.
     En v1 el portal puede derivar, como maximo: {code: codigo de producto OD/OI si fue cargado,
     quantity: 1}. El enriquecimiento (descripcion, etc.) es responsabilidad del middleware.
- Fechas: se almacenan como TIMESTAMPTZ (UTC) y 'date' se entrega en ISO 8601 con offset horario (ej.:
  2026-08-28T10:30:00-03:00). Si la integracion requiere UTC puro, se acuerda al definir el contrato.
- El ejemplo de RF-48 se conserva como formato objetivo de la integracion, con la salvedad de que los
  campos listados arriba se completaran recien cuando se acuerde con el middleware quien los provee.

PC-5. Identificador unico de la orden (aclara RF-48, RF-49, RF-50 y el esquema de base de datos)
- La orden tiene DOS identificadores con roles distintos:
  a) order_number (campo 'Numero de Orden' del formulario, RF-08): identificador de negocio que asigna el
     cliente; es unico en el sistema (constraint UNIQUE) y es el que se muestra en las pantallas.
  b) external_id: UUID generado por el portal (columna orders.external_id con DEFAULT gen_random_uuid()).
     Es el identificador tecnico/canonico de la orden para TODA la integracion: se entrega en el JSON
     como 'externalId' y es el valor que el middleware debe usar SIEMPRE en el path del PUT /sync.
- Aclaracion sobre el ejemplo de RF-48: ahi 'externalId' aparece como '98765' (parece un numero interno,
  no un UUID). Se aclara que externalId SIEMPRE es el UUID del portal. Si el middleware necesita exponer
  un codigo propio adicional, se agrega como campo nuevo acordado; no se reutiliza externalId.
- El PUT /sync (RF-49/RF-50) busca la orden por external_id (UUID). order_number no se usa en la
  integracion.

CORRECCIONES MENORES AL DOCUMENTO (no cambian requerimientos; solo redaccion y consistencia)
- RF-45: la Opcion B queda sin efecto (ver PC-1). 'En proceso' no debe usarse como estado.
- Frontend, componentes: la accion 'ver detalle, editar solo admin' corresponde a la GESTION DE USUARIOS
  (administrador). Las ordenes jamas se editan para ningun rol (RF-17, RF-22, RF-32).
- Valores de montura: normalizar la escritura (ej. 'SEMI-AEREA' / 'AL AIRE') en el formulario, en el CHECK

- Tabla api_keys: RF-40 define una unica API Key estatica. En v1 se utiliza una sola fila activa; la tabla

  a) Al crear un usuario o al resetear su contrasena, el flag queda en TRUE.
  b) Al iniciar sesion con el flag en TRUE, el usuario puede ejecutar UNICAMENTE el cambio de contrasena; el
     resto de los recursos autenticados responde 403 hasta completarlo.
  c) Al completar el cambio, el flag pasa a FALSE y el usuario obtiene acceso normal con su nueva contrasena.

ARQ-1. Arquitectura modular por caracteristicas (Feature-based Modular Architecture)
- Backend (Node/Express): el codigo se organiza en MODULOS por dominio/caracteristica bajo
  /backend/src/modules/<modulo>/. Cada modulo encapsula TODO lo propio:
  a) routes (definicion de rutas del modulo),
  b) controllers (manejo HTTP: entrada/salida; delegan en servicios),
  c) services (logica de negocio),
  d) dto/schemas (validacion express-validator y esquemas de entrada/salida),
  e) tests unitarios junto al modulo.
- Modulos previstos en v1: auth (login, cambio de contrasena obligatorio, middlewares), users (gestion de
  usuarios del administrador, RF-23 a RF-27), orders (dominio de ordenes, RF-05 a RF-17, incluye company
  autopoblada por DEC-3), external-orders (contrato PULL del middleware: GET /pending, PUT /sync y
  serializacion canonica; RF-35 a RF-56 y reglas R1-R5) y reports (estadisticas y exportacion, RF-33/RF-34).
- Capa transversal compartida (/backend/src/core): configuracion (env), cliente Prisma, manejo de errores,
  logger (morgan), middlewares globales (auth, roles, api-key, errores) y utilidades. Cada modulo de negocio
  expone su router montado en /api/<modulo> y sus servicios publicos; los modulos de negocio NO importan
  implementaciones internas de otros modulos de negocio (consumen sus servicios publicos), manteniendo bajo
  acoplamiento: un cambio dentro de un modulo no debe forzar cambios en los demas.
- Frontend (React/Vite): mismo criterio bajo /frontend/src/features/<feature>/. Cada feature contiene pages,
  components, hooks, api (cliente HTTP de la feature), types y tests. Features previstas: auth (login y
  cambio de contrasena obligatorio), orders-client (dashboard, formulario, historial y detalle del cliente),
  orders-lab (listado del laboratorio), admin-users, admin-orders, admin-stats. Capas transversales:
  /frontend/src/app (layout, rutas y guards por rol), /frontend/src/shared (componentes UI reutilizables:
  tabla, modales, filtros, confirm, graficos), /frontend/src/core (cliente HTTP con manejo de 401 y
  sesion/token).
- Estructura de referencia de la raiz del repositorio:
  /backend/src/modules/<modulo>/{routes,controllers,services,dto,tests}
  /backend/src/core
  /frontend/src/features/<feature>/{pages,components,hooks,api,types,tests}
  /frontend/src/app | /frontend/src/shared | /frontend/src/core
  /infra (docker, compose, nginx, certificados y scripts de despliegue)

ARQ-2. Containerizacion Docker con paridad local/produccion
- Versiones unicas y fijas: Node 20 LTS y PostgreSQL 16 en desarrollo, CI y produccion (mismas imagenes
  base con tag fijo). Todo el desarrollo local se ejecuta DENTRO de contenedores (no se requiere Node/npm
  en el host; solo Docker y git).
- Dockerfiles multi-stage por servicio:
  a) Backend: stage dev (base node:20, nodemon con hot-reload y bind-mount del codigo) y stage prod
     (instalacion de dependencias -> imagen final minima de runtime que arranca la API).
  b) Frontend: stage build (node:20 compila el bundle estatico con Vite) y stage prod: el bundle se sirve
     como contenido estatico (via el proxy inverso Nginx de produccion; no por Node).
- docker-compose.yml (desarrollo): servicios db (postgres:16 con volumen), api (backend con bind-mount y
  hot-reload) y frontend (dev server de Vite con proxy /api hacia el backend), todos con healthcheck.
  Comandos de referencia: docker compose up; docker compose exec api npm test.
- docker-compose.prod.yml (produccion, se materializa en la Fase 8): servicios api, frontend (estatico),
  db, proxy (Nginx) y red interna de Docker; al exterior solo se exponen los puertos 80/443 a traves del
  proxy. Secretos por variables de entorno; nunca en imagenes ni en el repositorio.

ARQ-3. Despliegue, dominio y SSL/HTTPS (produccion)
- Topologia v1: un servidor VPS con Docker Engine; contenedores api, frontend (estatico), db y proxy
  inverso. El proxy inverso (Nginx, elegido por defecto) es el UNICO punto de entrada publico:
  a) Termina SSL/TLS (HTTPS) para el dominio oficial.
  b) Redirige HTTP -> HTTPS.
  c) Enruta https://<dominio>/ hacia el frontend estatico y https://<dominio>/api/ hacia el backend; los
     endpoints del middleware (/api/external-orders/...) quedan disponibles solo por HTTPS via el proxy.
- Dominio oficial: se asocia el dominio real del proyecto al servidor (registro DNS A/AAAA apuntando a la
  IP publica del VPS). El dominio se define y verifica ANTES de emitir certificados; <dominio> es un
  placeholder que se reemplaza por el dominio oficial en toda configuracion.
- SSL/TLS: certificados validos de autoridad publica Let's Encrypt emitidos y renovados automaticamente con
  Certbot integrado al Nginx; renovacion programada (timer/cron) y verificacion por dry-run. NO se usan
  certificados autofirmados en produccion: se evitan los avisos de 'Sitio no seguro' y los bloqueos de
  navegadores/clientes por firmas no confiables.
- Seguridad de red: firewall del servidor con 22 (SSH de administracion), 80 y 443; la base de datos corre
  en la red interna de Docker sin puerto publico; healthchecks por servicio; logs accesibles; backups
  periodicos de PostgreSQL fuera del contenedor.
- Alternativas admitidas para el futuro (no implementadas en v1): Caddy o Traefik como proxy con TLS
  automatico, y Cloudflare como CDN/proxy frontal. La configuracion oficial del proyecto es Nginx + Certbot.
